## 발견된 비용 문제 (리소스별 상세)

### Auto Scaling warm-up 미설정으로 인한 cascade scale-out
autoscaling-group-h128pu에서 default_instance_warmup이 설정되지 않아 새 인스턴스가 트래픽을 받기 전 준비 시간 없이 즉시 로드밸런서에 등록됩니다. 이로 인해 초기 높은 CPU 사용률로 인한 연쇄적인 스케일 아웃이 발생하여 단시간에 과잉 인스턴스가 생성되고 불필요한 비용이 발생합니다.

### EC2 인스턴스 과잉 프로비저닝
2개의 Launch Template이 모두 m5.xlarge (4 vCPU, 16GB RAM, $0.192/hr)로 설정되어 있습니다. 게임 백엔드 워크로드의 일반적인 CPU 사용률을 고려할 때, 평균 사용률이 30% 미만일 경우 m5.large ($0.096/hr)로 다운사이징하여 인스턴스당 50% 비용 절감이 가능합니다.

### 태그 없는 리소스로 인한 비용 배분 불가
2개 Launch Template에 Environment, Owner, Project, Team 등 필수 태그가 누락되어 있어 개발/운영 환경별, 팀별 비용 배분과 추적이 불가능합니다. 이는 비용 거버넌스와 책임 소재 추적에 문제가 됩니다.

## 근본 원인 분석

레거시 설정이 남아있는 초기 클라우드 성숙도 단계에서 발생하는 전형적인 문제들입니다:

1. **자동화 스케줄링 미적용**: Auto Scaling warm-up 설정 부재로 인한 비효율적 스케일링 패턴
2. **태깅 거버넌스 부재**: 필수 태그 정책 미적용으로 비용 배분과 추적 불가
3. **개발/운영 환경 설정 혼용**: 환경별 인스턴스 타입 차별화 없이 모든 환경에 동일한 스펙 적용

## 개선 방안 (우선순위 순)

### 1. Auto Scaling warm-up 설정 추가 (즉시 적용 가능)
- `autoscaling-group-h128pu`에 `default_instance_warmup = 300` 추가
- 새 인스턴스가 트래픽을 받기 전 5분간 준비 시간 확보
- cascade scale-out 방지로 불필요한 인스턴스 생성 20% 감소 예상

### 2. 인스턴스 타입 rightsizing (메트릭 검토 후 적용)
- CloudWatch에서 평균 CPU 사용률 30% 미만 확인 시 m5.xlarge → m5.large 다운사이징
- 인스턴스당 월 $35 절감 ($0.192/hr → $0.096/hr)
- 총 6개 인스턴스 (desired_capacity 2+4) 적용 시 월 $210 절감

### 3. 태그 거버넌스 구축
- 모든 Launch Template에 Environment, Owner, Project 태그 추가
- 비용 배분 추적 및 책임 소재 명확화
- 향후 환경별 비용 최적화 정책 수립 기반 마련

### 4. 환경별 인스턴스 타입 차별화
- 개발 환경의 경우 t3.large 등 burstable instance 검토
- 운영 환경 대비 50-70% 비용 절감 가능
