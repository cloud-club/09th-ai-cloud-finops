## 1. 문제 식별

### 고아 EBS 스냅샷 210개 방치

- **210개의 EBS 스냅샷**이 존재하며, **전부** `SourceVolumeStatus = "deleted"` 태그를 갖고 있음
- 원본 EBS 볼륨이 이미 삭제되었지만, 해당 볼륨에서 생성한 스냅샷은 삭제되지 않고 계속 과금 중
- 모든 스냅샷의 `volume_id`가 `vol-placeholder`로, 실제 연결된 볼륨이 없음
- 스냅샷 스토리지 크기 샘플:
  - `ebs-snapshot-4vlwk5`: 2,010 GB
  - `ebs-snapshot-ll6zzs`: 1,937 GB
  - `ebs-snapshot-qzsof5`: 51 GB
- 모든 스냅샷의 표준편차가 0, 추세 "stable" → **아무도 사용하지 않고 있음**

## 2. 근본 원인 분석

### 스냅샷 라이프사이클 관리 부재

1. **볼륨 삭제 시 스냅샷 미삭제**: EC2 인스턴스나 EBS 볼륨을 종료/삭제할 때, 해당 볼륨에서 생성된 스냅샷을 함께 정리하는 프로세스가 없었음
2. **자동화된 정리 정책 부재**: AWS Data Lifecycle Manager(DLM) 등 스냅샷 보존 정책이 설정되지 않아, 한번 생성된 스냅샷이 영구 보관됨
3. **레거시 인프라 잔재**: README에서 언급된 "레거시 설정이 남아있는 단계"에 해당하며, 과거 운영 중 생성된 스냅샷이 정리되지 않고 누적됨
4. **가시성 부족**: 210개라는 대량의 스냅샷이 관리 사각지대에 놓여 있었음

## 3. 권장 조치

### 즉시 조치 (Quick Win)

#### 3-1. 고아 EBS 스냅샷 전량 삭제
- `SourceVolumeStatus = "deleted"` 태그가 있는 **210개 스냅샷 전량 삭제**
- 원본 볼륨이 이미 삭제되어 스냅샷의 복원 대상이 없으므로 보존 가치 없음
- Terraform에서 해당 리소스 블록을 모두 제거한 뒤 `terraform apply` 실행

#### 3-2. 스냅샷 라이프사이클 정책 수립
- **AWS Data Lifecycle Manager(DLM)** 도입으로 스냅샷 자동 생성/만료 관리
- 보존 기간 정책 설정 (예: 최근 7일 또는 최근 5개만 유지)
- 볼륨 삭제 시 관련 스냅샷을 함께 정리하는 자동화 스크립트 구축

#### 3-3. 정기 감사 프로세스 도입
- 월 1회 고아 스냅샷(원본 볼륨 삭제됨) 자동 탐지 스크립트 실행
- CloudWatch 또는 AWS Config Rules로 미사용 스냅샷 알림 설정

## 5. 전체 요약 (경영진 보고용)

TrackPulse의 인프라에서 **이미 삭제된 EBS 볼륨에 대한 스냅샷 210개**가 정리되지 않고 방치되어 매월 약 **$124.50**의 불필요한 비용이 발생하고 있습니다.

이 스냅샷들은 원본 볼륨이 삭제되어 복원 용도로 사용할 수 없으며, 접근 기록도 전혀 없어 완전한 낭비입니다. 즉시 전량 삭제하여 **연간 약 $1,494를 절감**할 수 있으며, 향후 동일 문제 재발 방지를 위해 AWS Data Lifecycle Manager 기반의 스냅샷 자동 관리 정책을 도입해야 합니다.

이는 금액 자체는 크지 않으나, **스냅샷 관리 거버넌스 부재**라는 구조적 문제를 드러내며, 규모가 커질수록 비용 누수가 가속화될 수 있는 리스크를 내포하고 있습니다.
